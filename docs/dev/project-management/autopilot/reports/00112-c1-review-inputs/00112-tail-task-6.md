### Findings (verbatim)
- ⚪ src/tools/backup/capabilities/tar_archive.py:522: In the system-tar path, `on_finalize()` runs before fsync/chmod/`os.replace`. An `OSError` there returns a fallback reason, the Python writer then re-archives the whole tree and emits a second `finalizing`. No `archiving` event is re-emitted, so the status shows "finalizing" for the entire fallback write. This is a rare edge case, but the phase is misleading while it lasts (found by: ALICE, BLAKE, BOB)
- 🟡 src/tools/backup/capabilities/tar_archive.py:48: `_archive_callbacks` is named like a pure factory, but calling it emits the initial `archiving` event and starts the throttle clock. It also returns `on_finalize` even when `progress is None`, while `on_bytes` is gated. Rename it to state the side effect (e.g. `_start_archive_progress`) or emit the boundary event explicitly in `_archive_result` (found by: ALICE, BOB)

### Scope and acceptance
Preserve the existing stream-close finalizing boundary and all archive/fallback data semantics. Re-emit activity-only archiving (done_bytes=None, total preserved) before Python fallback after system tar emitted finalizing. Keep fallback activity-only, including when the Python writer runs. Rename the progress helper to state its boundary-emission side effect; preserve its callback shape and throttle behavior. Add a regression test that fails against the current misleading post-close OSError fallback phase.
